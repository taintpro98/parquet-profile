Ba phương án ở cấu hình tốt nhất hiện có

Sau báo cáo final, hai phương án RocksDB bật thêm ZSTD dictionary của RocksDB để nén tốt hơn. java-parquet-duckdb giữ cấu hình. Đo trên dữ liệu lặp, một ngày 1M dòng.

Java và Go bật dictionary như nhau (đo fair, cùng tham số): file OFF 5,9 GB = 5,9 GB, ON 5,7 GB = 5,7 GB (-4,8%). sst_dump xác nhận cả hai ghi cùng tham số native và có khối dictionary. Nhận định trước đây rằng Java không bật được dictionary là sai.

Tra cứu gần như không đổi khi bật: 1000 key Java 1,00 s → 1,07 s, Go 0,44 s → 0,44 s. Cái giá là dump chậm hơn (Java 467 s → 497 s, Go 309 s → 337 s).

Khác biệt Java–Go không nằm ở nén mà ở tốc độ và RAM: Go tra 1000 key nhanh hơn ~2 lần, dump nhanh hơn ~1,5 lần, RAM dump ~3 lần ít hơn.

Dictionary 64 KB nén thêm được: trên go-rocksdb file 5,4 GB (-8,9%) so với -4,8% của 16 KB, tra không chậm hơn. java-parquet-duckdb không đổi cấu hình: file 5,3 GB, tra 1000 key 43,0 s.

So sánh 3 phương án

Ô tô xanh là tốt nhất trong hàng. Thời gian là trung vị, RAM là đỉnh (RSS cả tiến trình), tra cứu có 1 lần làm nóng rồi đo 3 lần. Mỗi bản ghi trả về được so từng byte với Oracle.

java-rocksdbBật ZSTD dictionary như bản Go, đặt qua parser options native (ColumnFamilyOptions.getColumnFamilyOptionsFromProps, chế độ nghiêm ngặt) cho cả compression_opts và bottommost_compression_opts; block 64 KB, index và bloom phân vùng; ojdbc lô 10.000. Đặt dictionary qua CompressionOptions của rocksdbjni: lớp này thiếu max_dict_buffer_bytes, RocksDB sẽ giữ cả file trong RAM để lấy mẫu. Gọi lại setCompressionOptions sau khi parse: ghi đè mất giới hạn.
java-parquet-duckdbGhi dữ liệu đã sort theo REFERENCE (đang làm, nhờ đó mỗi key chỉ đọc 1 row group); chạy thành service thường trực để không trả ~1,4 s khởi động JVM và DuckDB ở mỗi lần tra; gom key tra theo lô vào một câu IN (...). Bloom filter và page index (đã thử, phương án parquet-lookup): file to hơn, tra không nhanh hơn. Kỳ vọng tra nhanh như RocksDB: không đạt được (mục dưới).

Vì sao Parquet tra chậm, và không sửa triệt để được

java-parquet-duckdb, dữ liệu lặp1M dòng2M dòngTăng theo kích thước file?
Tra 1 key1,76 s1,70 sKhông
Tra key không tồn tại1,55 s1,58 sKhông
Tra 1000 key43,0 s85 sCó, gấp đôi khi file gấp đôi
  • Parquet lưu theo cột, nén theo row group (~21k dòng, ~117 MB). Lấy 1 bản ghi đủ 73 cột phải giải nén nguyên row group chứa nó.
  • Tra 1 key không tăng theo file: dữ liệu đã sort nên min/max của từng row group chỉ ra đúng 1 row group (đo được: quét 1/48 ở 1M, 1/96 ở 2M). Thời gian gồm ~0,4 s khởi động JVM, ~1 s mở DuckDB, ~0,2 s truy vấn.
  • Tra 1000 key tăng theo file: 1000 key ngẫu nhiên chạm gần hết row group, nên đọc gần cả file; file gấp đôi thì phải giải nén gấp đôi.
  • RocksDB lưu theo dòng, đơn vị nén là block 64 KB (~3 bản ghi): 1000 key chỉ đọc ~1000 block nhỏ, không phụ thuộc kích thước file.
  • Không sửa triệt để được vì đây là bản chất của định dạng theo cột. Row group nhỏ hơn giảm byte mỗi lần tra nhưng footer (metadata mọi row group) to ra, làm chính tra 1 key tăng theo file, và nén kém đi. Service thường trực bỏ được phần khởi động, mỗi key vẫn ~0,2 s so với vài ms của RocksDB.

ZSTD dictionary là gì

  • RocksDB lưu theo dòng, nén từng block 64 KB (~3 bản ghi) độc lập. Mỗi block bắt đầu với "trí nhớ" rỗng nên các chuỗi lặp khắp file ("khoản", BRANCH_00, tên cột JSON…) phải ghi lại ở từng block. Parquet nén cả cột của ~21k dòng một lần nên không bị như vậy.
  • Bật dictionary: lúc ghi, RocksDB lấy mẫu dữ liệu (tối đa 64 MB), train một từ điển 64 KB, lưu một lần trong file; mọi block nén và giải nén dựa trên từ điển đó. Block vẫn nhỏ nên tra vẫn nhanh.
  • Là tuỳ chọn chuẩn của RocksDB (max_dict_bytes, zstd_max_train_bytes, max_dict_buffer_bytes); file đọc được bằng RocksDB thông thường.

So sánh fair Java và Go, dictionary OFF / ON

Theo đề xuất của sếp: cùng dữ liệu 1M dòng, cùng key và value JSON, cùng đường ghi (SstFileWriter rồi ingest, một writer), cùng tham số nén đặt cho cả compression_opts và bottommost_compression_opts:

  • OFF: ZSTD mức 3, không dictionary.
  • ON: ZSTD mức 3, dictionary 16 KB, mẫu train 2 MB, buffer lấy mẫu 16 MB, ZSTD trainer.

Java đặt tham số qua parser options native (getColumnFamilyOptionsFromProps, chế độ nghiêm ngặt) vì lớp CompressionOptions của rocksdbjni không có max_dict_buffer_bytes. Mỗi ca dump 3 lần lấy trung vị; tra cứu 1 lần làm nóng rồi 3 lần. Sau mỗi dump, sst_dump xác nhận tham số đã xuống native và file có khối dictionary.

Java đọc Oracle lô 1.000 như Go

Thử bỏ khác biệt về lô đọc: chạy lại dump Java (dictionary ON) với ORACLE_FETCH_SIZE=1000, 3 lần lấy trung vị. RAM giảm phần bộ đệm của lô lớn, thời gian và CPU không đổi: lô đọc không phải lý do Java chậm hơn Go. Cách bật và giới hạn

  • Cả hai bản RocksDB: ROCKSDB_ZSTD_DICT_BYTES=65536. Tuỳ chọn thêm: ROCKSDB_ZSTD_TRAIN_BYTES (mặc định 100 × dict), ROCKSDB_ZSTD_BUFFER_BYTES (mặc định 64 MiB), ROCKSDB_ZSTD_LEVEL. Không đặt thì giữ cấu hình cũ.
  • Đã xác nhận bằng sst_dump --show_properties trên file 100k dòng: Java và Go ghi cùng tham số native (max_dict_bytes=65536; zstd_max_train_bytes=6553600; max_dict_buffer_bytes=67108864), file SST có khối rocksdb.compression_dict; bản tắt dictionary không có khối này.
  • Chưa thử bộ tham số nhỏ hơn (dictionary 16 KB, mẫu 2 MB, buffer 16 MB): RAM khi dump có thể thấp hơn, độ nén cần đo lại.
  • Cái giá: dump chậm hơn khoảng 25% (go-rocksdb), RAM khi dump tăng do giữ mẫu để train. Phần mẫu có giới hạn cứng nên RAM không nên tăng theo số dòng; chưa đo ở 2M để xác nhận.
  • Chỉ đo ở 1M dòng dữ liệu lặp; dữ liệu thật lặp nhiều hơn nên dictionary có thể còn lợi hơn.
