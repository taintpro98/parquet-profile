Ba phương án ở cấu hình tốt nhất, đo trong cùng một phiên

Mọi số trong trang này đến từ một phiên đo duy nhất: cùng máy, cùng dữ liệu (seed cố định 20261117, một ngày 1M dòng, dữ liệu lặp), cùng giao thức, cùng lô đọc Oracle 1.000. Mỗi phương án dùng cấu hình tốt nhất tìm được ở bước chọn cấu hình bên dưới.

go-rocksdb là phương án tốt nhất theo ưu tiên thời gian ≈ dung lượng > RAM: tra 1 key 0,02 s, 1000 key 0,37 s, file 5,4 GB, RAM khi dump 293 MB.

java-rocksdb ra file như go-rocksdb (5,4 GB, cùng tham số nén, sst_dump xác nhận) nhưng tra 1000 key 0,79 s (2,2 lần so với Go), dump 403 s so với 335 s, RAM dump 605 MB so với 293 MB.

java-parquet-duckdb có file nhỏ nhất (5,3 GB; go-rocksdb lớn hơn 2,5%) nhưng tra 1000 key 42,8 s (116,6 lần so với Go) và tăng theo kích thước file.

So sánh 3 phương án

Ô tô xanh là tốt nhất trong hàng. Dump 3 lần lấy trung vị; RAM là đỉnh lớn nhất của 3 lần (RSS cả tiến trình); tra cứu có 1 lần làm nóng rồi đo 3 lần. Mỗi bản ghi trả về được so từng byte với Oracle.

Thời gian tra bản Java gồm khoảng 0,4 s khởi động JVM, java-parquet-duckdb thêm khoảng 1 s mở DuckDB (giải nén thư viện native). Trong service chạy lâu các khoản này chỉ trả một lần. Hai bản RocksDB dùng hai bản native khác nhau: rocksdbjni đóng gói 11.8.1, Go dùng librocksdb 11.13.2 (Homebrew).

Vì sao go-rocksdb nhanh hơn java-rocksdb dù cùng file

  • Phần lõi giống nhau: cùng thư viện C++ RocksDB, cùng định dạng và tham số nén, file ra bằng nhau (5,4 GB); đọc và giải nén block tốn như nhau.
  • Tra cứu: chênh lệch chủ yếu là khởi động JVM. Tra key không tồn tại (gần như chỉ còn khởi động và mở DB): Java 0,41 s, Go 0,02 s. Trừ khoản đó, tra 1000 key còn Java 0,38 s so với Go 0,35 s (+8,0%): phần tra thật gần như bằng nhau. Chạy thành service thường trực thì Java không còn khoản khởi động.
  • Dump: Java chậm hơn 20,4% (403 s so với 335 s), CPU 244 s so với 191 s, RAM 605 MB so với 293 MB (JVM có heap nền, chuỗi UTF-16, và dữ liệu đi vòng qua String rồi chép qua JNI, trong khi Go đi từ byte ra byte).
  • Bước tạo JSON đo riêng, ngoài bộ bench, dữ liệu tổng hợp 70 cột × 300 ký tự, tính cho 1M dòng: Java bản cũ (StringWriter khoá đồng bộ từng ký tự và String.format mỗi cột) 230 s, Java sau khi sửa (StringBuilder, tiền tố cột dựng sẵn) 70,6 s, Go 54 s. Bản Java trong bảng trên đã dùng code sau khi sửa.
  • Phần dump còn lại của Java chưa profile để tách riêng từng khoản (chuyển chuỗi, JNI, GC).

Chọn cấu hình tốt nhất

Mỗi cấu hình ứng viên dump 1 lần rồi tra, trên cùng dữ liệu. Chọn theo ưu tiên thời gian ≈ dung lượng > RAM; riêng cấu hình nén, dung lượng nặng hơn: chấp nhận thời gian tăng vài %.

16 KB: train 2 MB, buffer 16 MB (đề xuất của sếp). 64 KB: train 6,4 MB, buffer 64 MB.

Dictionary 64 KB: file -9,1% so với không dictionary (16 KB, bộ tham số sếp đề xuất: -4,7%), tra 1000 key bằng nhau giữa 16 KB và 64 KB. Cái giá của dictionary: tra 1000 key +12,1% (0,33 s → 0,37 s) và dump +19,9% (279 s → 334 s, một lần lúc ghi); RAM dump tăng do giữ mẫu để train, có giới hạn cứng nên không tăng theo số dòng. Chọn 64 KB vì file nhỏ hơn rõ rệt trong khi chênh lệch tra chỉ vài chục ms cho 1000 key; nếu ưu tiên thời gian tra tuyệt đối hơn dung lượng thì tắt dictionary vẫn là lựa chọn hợp lệ.

Vì sao Parquet tra chậm, và không sửa triệt để được

java-parquet-duckdb, dữ liệu lặp1M dòng2M dòngTăng theo kích thước file?
Dung lượng file5,3 GB10,6 GBCó (đương nhiên)
Tra 1 key1,54 s1,72 sKhông đáng kể (+0,2 s)
Tra key không tồn tại1,46 s1,55 sKhông đáng kể (+0,1 s)
Tra 1000 key42,8 s86 sCó, gấp ~2 lần khi file gấp đôi
  • Parquet lưu theo cột, nén theo row group (~21k dòng, ~117 MB). Lấy 1 bản ghi đủ 73 cột phải giải nén nguyên row group chứa nó.
  • Tra 1 key gần như không tăng theo file: dữ liệu đã sort nên min/max của từng row group chỉ ra đúng 1 row group (chỉ tăng chút do footer to hơn).
  • Tra 1000 key tăng theo file: 1000 key ngẫu nhiên chạm gần hết row group, nên đọc gần cả file; file gấp đôi thì phải giải nén gấp đôi.
  • RocksDB lưu theo dòng, đơn vị nén là block 64 KB (~3 bản ghi): 1000 key chỉ đọc ~1000 block nhỏ, không phụ thuộc kích thước file.
  • Không sửa triệt để được vì đây là bản chất của định dạng theo cột: tăng số luồng DuckDB không làm nhanh hơn, còn đổi codec chỉ đánh đổi dung lượng lấy thời gian (xem bảng chọn cấu hình).

ZSTD dictionary là gì

  • RocksDB lưu theo dòng, nén từng block 64 KB (~3 bản ghi) độc lập. Mỗi block bắt đầu với "trí nhớ" rỗng nên các chuỗi lặp khắp file ("khoản", BRANCH_00, tên cột JSON…) phải ghi lại ở từng block. Parquet nén cả cột của ~21k dòng một lần nên không bị như vậy.
  • Bật dictionary: lúc ghi, RocksDB lấy mẫu dữ liệu, train một từ điển nhỏ, lưu một lần trong file; mọi block nén và giải nén dựa trên từ điển đó. Block vẫn nhỏ nên tra vẫn nhanh.
  • Là tuỳ chọn chuẩn của RocksDB (max_dict_bytes, zstd_max_train_bytes, max_dict_buffer_bytes); file đọc được bằng RocksDB thông thường.
